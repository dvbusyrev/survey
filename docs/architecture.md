# Простая схема слоёв

Проект рассчитан на небольшое внутреннее приложение, поэтому базовая схема для новых и изменяемых модулей:

```text
Controller -> FeatureService -> Dapper SQL
```

Правила:

- `Controller` принимает HTTP-запрос, проверяет входные данные на уровне веба и возвращает ответ.
- `FeatureService` содержит сценарий целиком: бизнес-правила, транзакцию, Dapper SQL и формирование результата.
- SQL держим рядом со сценарием, если он используется только этим сценарием.
- Отдельный repository добавляем только если один и тот же SQL реально нужен нескольким feature services или модуль уже стал слишком большим.
- Интерфейс добавляем только для внешней зависимости или системного шва: время, текущий пользователь, подключение к БД, почта, криптография, файловое хранилище.
- DTO и mapper не создаём автоматически. Используем простые модели запроса/ответа только когда они реально уменьшают связность или делают контракт понятнее.
- Новые слои не добавляем “на будущее”. Если появляется боль от дублирования, сначала смотрим на конкретный повтор и только потом выделяем общий код.

Цель правила: меньше файлов на один сценарий, проще поиск логики, быстрее правки интерфейса и бизнес-правил.

Порядок упрощения backend-модулей:

1. `Users`
2. `Organizations`
3. `Surveys`
4. `Answers`
5. `Theme`
6. `Email`
7. `Logs`

Для каждого модуля целевое состояние: один feature service, один понятный набор DTO/view models, SQL рядом в сервисе или в одном простом repository без дополнительной цепочки интерфейсов.
